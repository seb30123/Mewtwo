# Attack 04 — Ravi PC oracle on Kyber512 (sanity check phase)

> **Status** : ❌ Negative — no global timing oracle observable
> **Target** : Raspberry Pi 5 (Cortex-A76, AArch64) · liboqs 0.15.0 · Kyber512 ref / gcc 12.2.0 -O2
> **Method** : Welch t-test on `OQS_KEM_decaps` cycle counts, valid vs invalid ciphertexts
> **Result**  : Welch t = -1.17 (n=20 000), no statistically significant difference
> **Date**    : May 2026

---

## One-line summary

After 20 000 measurements with randomized ordering, the cycle count of
`crypto_kem_dec(Kyber512)` shows no detectable difference between valid
and invalid ciphertexts. The Fujisaki-Okamoto re-encryption check in
liboqs 0.15.0 is timing-balanced on Cortex-A76 with gcc 12.2.0 -O2.

---

## Background: why this matters

Imagine a safe that beeps "BEEP" when you enter the right code and "BOOP"
when you enter the wrong one. The safe doesn't tell you the code, but it
confirms yes/no on every attempt. With a million guesses, you eventually
crack it — pure brute force.

Modern CCA-secure KEMs are designed to **never beep BEEP/BOOP**. You're
not supposed to learn whether the ciphertext you submitted was valid or
not, otherwise the secret key leaks. Kyber achieves this via the
**Fujisaki-Okamoto (FO) transform**, which always returns a "secret-like"
output, real or fake.

**Unless implementation leaks somewhere.** The seminal paper by Ravi,
Roy, Bhasin, Chattopadhyay, Mukhopadhyay (TCHES 2020) showed that on
many platforms, the valid path and invalid path of FO touch different
memory or take different time, exposing a **plaintext-checking oracle**
(PC oracle). With a PC oracle, key recovery requires roughly 100 000
chosen-ciphertext queries.

This sanity check answers a single binary question : **is a PC oracle
detectable at the global timing level on our platform ?**

If yes → full attack reproduction is worthwhile.
If no → either the platform is naturally protected, or the leak is
sub-cycle and requires cache-level instrumentation.

## What we did

### Step 1 — Read the source

We inspected `crypto_kem_dec` in liboqs 0.15.0 (file
`src/kem/kyber/pqcrystals-kyber_kyber512_ref/kem.c`). The function does
exactly what the FO spec describes : decrypt, re-encrypt, compare via
`verify`, conditionally select the secret via `cmov`, hash with
SHAKE256.

The `cmov` function in `verify.c` includes a deliberate compiler
opacity barrier :

```c
__asm__("" : "+r"(b) : /* no inputs */);
```

This prevents gcc/clang from inferring that `b ∈ {0, 1}` and emitting a
branch on it. It's an anti-Clangover measure baked into the source.
See [`firmware/source-snippets/verify.c.snapshot`](firmware/source-snippets/verify.c.snapshot).

### Step 2 — Disassemble

`crypto_kem_dec` compiles to **208 bytes** (4 cache lines), with
explicit `bl` calls to `verify` and `cmov` — neither was inlined.

`cmov` itself is 460 bytes (8 cache lines), with three execution paths
generated by gcc :
- a NEON 16-byte vectorized loop (the one used for Kyber512's 32-byte
  buffer)
- a NEON 8-byte fallback
- a fully-unrolled scalar epilogue

For Kyber512, only the NEON 16-byte loop runs : exactly 2 iterations
covering the 32-byte `kr` buffer, with `bit` (bit-insert-if-true)
followed by an unconditional `str q0, [x0, x3]` store.

The store **always happens**. The difference between valid (`b=0`) and
invalid (`b=0xFF`) is whether the store writes the same value or a new
value to the stack. We hypothesized this could create a measurable
timing difference. See [`firmware/disasm/cmov_verify.disasm.txt`](firmware/disasm/cmov_verify.disasm.txt).

### Step 3 — Naive timing test (v1)

We measured `OQS_KEM_decaps` cycles for 1 000 valid and 1 000 invalid
ciphertexts, **strictly alternating**. Result : Welch t = +3.48,
p = 0.0005. Borderline significant.

**We didn't trust this result.** Strict alternation can interact with
branch predictors, prefetchers and cache state in ways that produce
artificial signal. So we ran v2.

### Step 4 — Robust timing test (v2)

Improvements:
- 10 000 ciphertexts per group instead of 1 000
- **Randomized order** via Fisher-Yates with cryptographic seed (instead
  of strict alternation)
- 200-iteration warmup instead of 100
- CPU temperature logged at start and end (start: 56.2°C, end: 56.2°C,
  delta 0.0°C — no thermal drift)
- 4-quartile breakdown to detect any temporal bias

**Result :**

| Metric | Value |
|---|---|
| Total measurements | 20 000 |
| Mean cycle count (valid) | 59 988.0 |
| Mean cycle count (invalid) | 59 995.9 |
| Difference | -7.87 cycles (-0.013 %) |
| Welch t-statistic | **-1.17** |
| p-value | 0.244 |
| TVLA threshold | 4.5 |
| Quartile t-values | -1.18, +0.84, -1.24, -0.71 |

The marginal v1 signal **disappeared and changed sign** in v2. Across
the 4 temporal quartiles, t-values fluctuate around zero with mixed
signs. This is the canonical signature of a **false positive caused by
the v1 protocol** (alternating order interacting with hardware
predictors), not a real oracle.

---

## Conclusion

**No PC oracle is detectable at the `OQS_KEM_decaps` global timing
level on Cortex-A76 with liboqs 0.15.0 and gcc 12.2.0 -O2.**

This generalizes our earlier finding from KyberSlash (attack 01) :
modern AArch64 + modern liboqs is timing-balanced for Kyber even on the
post-FO comparison branch.

This does **not** rule out :
- Cache-level leaks at the L1/L2/LLC granularity (the store in `cmov`
  could in theory be observable via Flush+Reload, but our HQC results
  in attack 02 suggest PQClean-style implementations don't leak this
  way either)
- EM or power side channels (different physical setup needed)
- SMT / cross-core attacks (Pi 5 has no SMT)
- Older or non-reference Kyber implementations

We document this as a **scientifically meaningful negative result** and
move on to the next attack in the catalog rather than invest weeks
chasing a leak that, if it exists, is too weak to be exploited in
practice.

## Reproduce this result

### Prerequisites

- Raspberry Pi 5
- Raspberry Pi OS 64-bit (kernel 6.12+)
- liboqs 0.15.0 built with `cmake -DOQS_USE_OPENSSL=ON -DCMAKE_BUILD_TYPE=Release`
- `perf_event_paranoid = 0`
- CPU governor set to `performance`

See [`firmware/disasm/environment.txt`](firmware/disasm/environment.txt)
for the exact environment of our session.

### Build

```bash
cd firmware/timing-sanity
gcc -O2 -Wall -std=c11 -I$HOME/liboqs/build/include \
    -o timing_sanity_v2 timing_sanity_v2.c \
    $HOME/liboqs/build/lib/liboqs.a -lcrypto -lpthread -lm
```

### Run

```bash
./timing_sanity_v2 > timing_v2.csv 2> timing_v2.log
# ~30 seconds for 20 000 decapsulations
```

### Analyze

```bash
python3 analyze_timing_v2.py timing_v2.csv
```

Expected output : `AUCUN ORACLE TIMING (|t| < 4.5)`.

## Limitations

This sanity check says nothing about :

- Other KEM families (Saber, FrodoKEM, NTRU) — each has its own FO
  branch worth analyzing
- Optimized Kyber implementations (AVX2, Neon-tuned variants) — different
  cache footprint
- SMT and cross-core adversary models — Pi 5 is single-thread per core
- Profiled deep-learning side-channel attacks — different methodology
- Implementations with masking countermeasures — not present in liboqs

See [`lab_notes.md`](lab_notes.md) for our full list of caveats and
unaddressed hypotheses.
